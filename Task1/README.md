# Задание 1. Целевая архитектура и приоритизация проблем

Кейс «Будущее 2.0»: медицинская компания с собственным банком, все данные в DWH на SQL Server 2008, отчёты строятся часами, впереди подключение фармацевтики и производителя электроники. Задача спринта - «витрина данных» и архитектура, при которой новые направления не требуют доработок центрального DWH.

Архитектура через год - домены с собственными средами в облаке плюс общая платформа данных самообслуживания:

- **Витрина данных** - портал самообслуживания и semantic-слой. Сотрудник сам строит отчёты по своим правам, без SQL и без очереди к команде DWH.
- **Платформа данных** - приём CDC и событий, обработка данных (потоковые и пакетные трансформации, форматно-логический контроль), lakehouse на S3 с Apache Iceberg, витрины доменов как дата-продукты с контрактом и каталог данных с lineage.
- **Домены**: финтех (существующие сервисы на Golang и Java, своя БД и бизнес-логика домена), клиники (портал сотрудников вместо PowerBuilder и сервис медицинских данных со своей логикой), ИИ-сервисы (существующая ML-платформа и feature store поверх операционных витрин, без содержания медкарт).
- **Интеграция**: API-шлюз с контрактами для партнёров. Функции ESB разъезжаются: транспорт, retry и DLQ - в брокер Kafka, потоки, пакеты и форматно-логический контроль - в обработку данных, бизнес-логика - в сервисы доменов.
- **Легаси** (DWH, ESB, PowerBuilder, Power BI поверх DWH) выводится в течение года, данные мигрируются в lakehouse.

На диаграмме отмечены три ключевых бизнес-сценария: С1 - быстрая отчётность (минуты вместо часов), С2 - независимое развитие финтеха и ИИ, С3 - масштабирование новых направлений контрактом с платформой, без новой логики в DWH. Медицинские карты, истории болезней и результаты исследований в аналитику не идут. Обезличивание этого запрета не снимает: в витрину клиник попадают визиты и загрузка, а не содержание карт.
