# Задание 4. Обоснование конфигурации Terraform

Диаграмма автоматизации развёртывания: [diagram.drawio](diagram.drawio), картинка - [diagram.png](diagram.png). Конфигурация: [main.tf](main.tf), [variables.tf](variables.tf), [outputs.tf](outputs.tf), [terraform.tfvars](terraform.tfvars).

## Что разворачивает конфигурация

Стенд целевой архитектуры из задания 1 в Yandex Cloud: сеть с подсетью, группа безопасности, загрузочные диски и две виртуальные машины - lakehouse-stand (стенд платформы данных) и portal-stand (стенд витрины). Связи учтены ссылками ресурсов: диск получает id образа из data-блока, виртуальная машина подключает свой диск и подсеть, группа безопасности привязана к интерфейсам.

## Управляется Terraform и вручную

**Terraform управляет полностью** (зелёное на диаграмме): провайдер Yandex Cloud, сеть, подсеть, группа безопасности, оба загрузочных диска, обе виртуальные машины с NAT-адресами. Всё описано декларативно, состояние фиксируется в terraform.tfstate.

**Остаётся за человеком** (серое на диаграмме): подстановка пути к авторизованному ключу сервисного аккаунта в terraform.tfvars перед запуском - файл ключа живёт только локально, в репозиторий идёт путь-плейсхолдер; DNS-записи витрины у регистратора; первичная загрузка исторических данных из DWH - это миграционный процесс этапа 4 роадмапа, а не создание инфраструктуры.

## Выбор ресурсов и параметров

- **Платформа standard-v3** - текущее поколение Intel Ice Lake, линейка с честным соотношением цена-производительность для универсальных нагрузок.
- **Стенды: 2 vCPU, 4 ГБ, network-hdd 10 ГБ каждый.** Для демонстрационного стенда этого достаточно: на диске операционная система и пакеты. Под нагрузку целевой архитектуры lakehouse-stand увеличивается до 4 vCPU, 8 ГБ и диска 40 ГБ, portal-stand остаётся на 2 vCPU и 4 ГБ с диском 20 ГБ. Тип диска тот же. Изменение - одна правка tfvars и apply, без переконфигурации кода.
- **Тип диска network-hdd.** Диск загрузочный и для стенда хранит систему и пакеты. Аналитические файлы озера на него не пишутся, поэтому пропускной способности HDD хватает, а 10 ГБ хватает на образ Ubuntu и пакеты. Под нагрузку растёт объём диска, а не его тип. Если узким местом станет именно чтение с загрузочного диска, тип меняется на network-ssd в tfvars, код трогать не нужно.
- **nat = true** на интерфейсах: стендам нужен исходящий доступ для установки пакетов и обновлений, а порталу - публичный адрес для демонстрации. В боевом контуре исходящий трафик доменов пойдёт через NAT-шлюз с фиксированными адресами, чтобы не выпускать каждую машину в интернет напрямую.
- **Группа безопасности** открывает наружу только SSH с адресов администраторов и HTTPS для портала. Список admin_cidrs по умолчанию ограничен одним адресом, 0.0.0.0/0 там нет.

## Почему декларативный подход

Конфигурация описывает целевое состояние - «какая инфраструктура должна существовать», а не последовательность шагов для её создания. Terraform сам вычисляет разницу между описанием и фактом из state-файла: `terraform plan` показывает план изменений до их применения, `terraform apply` приводит реальность к описанию. Повторный apply ничего не ломает - операция идемпотентна.

## Что даёт Infrastructure as Code

- **Воспроизводимость.** Стенд домена разворачивается той же конфигурацией с другими значениями переменных: для финтеха и клиник меняются только tfvars, ошибки «настроил руками и забыл» исключены. Откат к рабочей конфигурации - это apply предыдущей версии кода.
- **Масштабируемость.** for_each по переменной vms добавляет третий стенд одной записью в tfvars, без копирования блоков. Пересмотр конфигурации идёт через code review в git, как у кода приложений.
- **Прозрачность.** Весь контур описан в четырёх читаемых файлах; состояние хранится в tfstate, а выхлопные адреса стендов выводятся outputs - их забирают DNS-настройка и пайплайны выкатки.

## Как запустить

```
cd Task4
# в terraform.tfvars подставить путь к ключу, yc_cloud_id, yc_folder_id
terraform init
terraform plan -var-file=terraform.tfvars
terraform apply -var-file=terraform.tfvars
```

Все параметры запуска собраны в одном файле terraform.tfvars: путь к ключу сервисного аккаунта, идентификаторы облака и каталога, зона, адреса администраторов и параметры машин. После проверки `terraform destroy` убирает стенд целиком, а в файле значений перед коммитом в публичный репозиторий путь к ключу заменяется на плейсхолдер.
